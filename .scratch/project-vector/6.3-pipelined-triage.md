## Agent Brief

### Context
We are replacing the legacy `TriageSorter` with a unified `AgentPipeline`. This pipeline will allow jobs to be triaged (and later evaluated) in real-time as they are scraped, rather than waiting for a batch run. It also introduces a `ModelAdapter` to decouple our logic from specific LLM providers.

### What to build
1. **ModelAdapter (src/llm_client.py):**
   - A unified interface `generate_json(prompt, response_model)`.
   - Implement for Gemini using the existing `llm_client.py` logic but standardized.
2. **AgentPipeline (src/pipeline.py):**
   - An async runner that uses a `queue.Queue` (or `asyncio.Queue`).
   - `push(job_id)` adds a job to the queue.
   - `start_worker(concurrency=3)` runs background workers that pull from the queue.
   - Each worker executes a `Strategy`.
3. **TriageStrategy (src/pipeline.py):**
   - Implements `BaseStrategy`.
   - Defines the Triage prompt and Pydantic schema for the response.
   - Calls `repo.mark_triage_complete(job_id, score, analysis)` upon success.

### Implementation Notes
- **Resilience:** Wrap the strategy execution in a try-except. Log errors but don't stop the worker.
- **Rate Limiting:** Use `asyncio.Semaphore` in the pipeline to limit concurrent LLM calls.
- **Scraper Integration:** In `src/collector.py`, after a successful `upsert_job`, call `pipeline.push(job_id)`.

### Test Strategy
- **Mock Model:** Use a mock `ModelAdapter` that returns pre-defined JSON.
- **Concurrency Test:** Verify that the pipeline doesn't exceed the semaphore limit.
- **Persistence Test:** Verify that jobs with low scores are still updated in the DB with status 'discarded'.
