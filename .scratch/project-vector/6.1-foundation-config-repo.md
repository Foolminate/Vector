## Agent Brief

### Context
This is the foundational phase of the Project Vector architectural refactor. The goal is to replace shallow configuration and database modules with "Deep Modules" (Pydantic-based configuration and a domain-driven Job Repository).

### What to build
1. **AppConfig (src/config_loader.py):** Implement a Pydantic `BaseSettings` model that handles `SEARCH_CONFIG.yaml` and environment variables. Provide a `load()` class method.
2. **JobRepository (src/database.py):** Implement a domain-driven repository that owns the `Job` state machine.
   - Methods: `upsert_job()`, `get_pending_triage()`, `mark_triage_complete()`, `add_note()`, `log_action()`, `log_cost()`.
   - Transition Logic: `mark_triage_complete()` must internally decide the next status based on score (80+ = high-pass, 40-79 = edge-case).
3. **Schema Migration:** Create `migrations/v8_add_processing_and_notes.sql` to add `processing_status` (TEXT, default 'idle') and verify the `notes` column exists.
4. **Legacy Wrapper:** Maintain a `DatabaseManager` class that inherits from or wraps `JobRepository` to prevent breaking the TUI and other modules.

### Implementation Notes
- **Pydantic at the gate:** Use Pydantic for the `AppConfig`.
- **Deep Repository:** The repository should be the *only* place where SQL queries for jobs live.
- **Locality:** Move the state transition "magic numbers" (80, 40) into the repository.

### Test Strategy
- **Unit Tests:** Create `tests/test_foundation_refactor.py`.
- **Case 1:** Verify `AppConfig.load()` correctly parses the YAML.
- **Case 2:** Verify `JobRepository` migration runs and adds columns.
