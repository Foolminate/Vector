# PRD: QA & Robustness Adjustments

## Problem Statement
Project Vector's core backend pipeline lacks the robustness and architectural consistency required for production reliability. Key vulnerabilities include:
- Silent scraper failures and lack of explicit bot-detection.
- No schema validation for extracted data or LLM outputs, leading to potential data corruption.
- Inconsistent state machines and column usage between `sorter.py` and `database.py`.
- Invisible LLM retries and lack of a structured data retention/archival lifecycle.
- Insufficient testing of state transitions, race conditions, and error fallbacks.

## Solution
Reinforce the system with a unified data validation layer, a standardized state machine, and a multi-stage data lifecycle. This includes implementing Pydantic validation for all pipeline inputs/outputs, a database migration to unify schemas, a circuit-breaker for permanent failures, and a comprehensive test suite covering concurrency and time-dependent logic.

## User Stories
1. As a system administrator, I want the scraper to log specific job-level failures to the audit log, so I can identify and fix parsing or connectivity issues.
2. As a system administrator, I want the scraper to detect specific bot-blocking patterns (403s, CAPTCHA text) and halt execution gracefully.
3. As a developer, I want all data (Seek extraction, Triage results, Evaluation results) validated against Pydantic schemas before DB insertion.
4. As a system administrator, I want LLM retries and "permanent failure" states recorded in the audit log.
5. As a system administrator, I want a two-stage data retention policy: soft-archive jobs after 30 days and hard-purge after 90 days.
6. As a developer, I want to ensure the Sorter and Repository use the same status vocabulary (`discarded`) and fields (`analysis_json`).
7. As a developer, I want unit tests for the triage logic that verify behavior when `DOCTRINE.md` is missing or malformed.
8. As a developer, I want database tests that verify transactional integrity and `ON CONFLICT` behavior under concurrent load.
9. As a developer, I want to verify the 30-day purge logic using time-shifted test data.

## Implementation Decisions

### Modules & Interfaces
- **`src/models.py` (New):**
    - `RawJobData`: Scraper extraction schema.
    - `TriageResult`: Agent 1 output schema (score, rationale).
    - `EvaluationResult`: Agent 2 output schema.
- **`src/database.py` (JobRepository):**
    - Migration `v10`: Add indices on `seek_job_id` and `created_at`; unify `rationale` into `analysis_json`.
    - Standardize status: Use `discarded` consistently (replacing `rejected`).
    - Implement `archive_and_purge()`: Soft-delete (`archived`) at 30 days, hard-purge at 90.
    - Move `upsert_job` and `log_action` into a single atomic transaction.
- **`src/collector.py` (SeekCollector):**
    - Implement bot-detection triggers: `status == 403`, presence of "CAPTCHA", or specific timeout patterns.
- **`src/llm_client.py` (ModelAdapter):**
    - Implement a circuit-breaker: after max retries, set `processing_status = 'failed-permanent'`.

### Technical Decisions
- **Validation:** Pydantic V2 enforced at all module boundaries.
- **State Machine:** Unified statuses: `new`, `high-pass`, `edge-case`, `discarded`, `archived`.
- **Atomic Transactions:** Use SQLite context managers to ensure all-or-nothing updates for scraper results.

## Testing Decisions
- **Standards:** Isolated mocking; >90% coverage for logic modules.
- **New Scenarios:**
    - **Concurrency:** Multiple scrapers hitting `upsert_job` simultaneously.
    - **Time-Travel:** Mocking `datetime.now()` to verify the 90-day hard-purge.
    - **Failure Modes:** Missing `DOCTRINE.md`, malformed LLM JSON (invalid types/scores).

## Out of Scope
- UI/TUI changes beyond status display updates.
- Support for job boards other than Seek NZ.
