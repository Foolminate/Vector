# PRD: Architectural Refactoring for Deep Modules & Pipelined Intelligence

## Problem Statement
The current Project Vector codebase suffers from "architectural friction" caused by shallow modules and leaked implementation details. SQL queries are scattered across functional modules, scraping logic is tightly coupled to DOM navigation, and AI agents are implemented as repetitive, hard-to-test loops. This makes the system brittle, difficult to test in isolation, and hard to scale to new job boards or additional AI analysis stages.

## Solution
We will refactor the system into a set of "deep modules" with high leverage. This includes:
1.  **Job Repository:** A single home for the Job domain state machine and persistence.
2.  **Resilient Parser Seam:** A pure extraction engine that separates "fetching" from "parsing."
3.  **Strategy-Based Agent Pipeline:** A unified, async-capable runner that orchestrates AI tasks via lightweight strategies rather than repetitive classes.
4.  **Typed Configuration:** A Pydantic-based configuration layer for robust validation.
5.  **Live TUI Feedback:** Updating the Review TUI to show real-time background processing status without visual bloat.

## User Stories
1. As a developer, I want all SQL queries concentrated in a Job Repository, so that I can change the schema without touching the scraping or AI logic.
2. As a developer, I want a pure Seek Parser that accepts HTML and returns JSON, so that I can test extraction logic with 100% reliability using static files.
3. As a developer, I want a unified Agent Pipeline, so that I can add new AI analysis stages by just defining a prompt and a schema.
4. As a developer, I want to use Pydantic for all configuration and LLM data validation, so that I get immediate feedback on malformed data.
5. As an operator, I want the system to process jobs in an async pipeline, so that triage and deep evaluation happen as jobs stream in, rather than waiting for the entire scrape to finish.
6. As an operator, I want the system to isolate and continue when a single LLM call fails, so that a one-off error doesn't halt the entire discovery run.
7. As an operator, I want the system to respect rate limits through a centralized semaphore, so that I don't get blocked by LLM providers.
8. As a TUI user, I want to see which jobs are currently being processed in the background via a visual icon and a progress indicator, so that I know the system is working and how much is left.
9. As a TUI user, I want to be able to interrupt a background triage or evaluation run gracefully, so that I can stop processing if needed.
10. As a TUI user, I want new jobs to be visually highlighted, so that I can quickly identify fresh opportunities.
11. As a TUI user, I want my manual notes to be reliably saved to the correct job record, so that my insights are preserved.
12. As a developer, I want to swap LLM providers via a Model Adapter, so that I can use the most cost-effective model for each specific task.
13. As an operator, I want the system to preserve all Agent 2 evaluation output even for rejected jobs, so that I can review the reasoning behind a "discarded" verdict.

## Implementation Decisions
- **Module: Job Repository:** Will replace the shallow `DatabaseManager`. It will own the state machine transitions (`new` -> `high-pass` -> `shortlisted`) and provide high-level methods like `get_pending_triage()`. It will explicitly handle the `notes` column and ensure `analysis_json` is persisted for all evaluations.
- **Module: Agent Pipeline:** A generic runner that manages async queues and LLM provider adapters. It will execute "Strategy" objects which define the specific prompt and schema. The pipeline will support streaming execution and provide progress updates.
- **Module: Seek Parser:** A pure extraction module that takes HTML/JSON and returns structured Job objects. It will include fixed logic for extracting `published_at` and `expiration_date`.
- **Module: AppConfig:** A Pydantic BaseSettings class that validates `SEARCH_CONFIG.yaml` and environment variables.
- **Interface: Model Adapter:** A unified interface for LLM calls (`generate_json(prompt, schema)`) that handles provider-specific SDKs (Gemini, OpenAI, etc.).
- **TUI Interaction:** Use Textual background workers to update the UI state. Transient processing state will be visually represented by modifying the job title (e.g., prepending an icon or spinner). The TUI will include a progress bar and an "Interrupt" capability for background tasks.
- **Parallelism:** Use Asyncio Queues to pipeline data from the Scraper to the Sorter and then to the Evaluator in real-time.
- **Bug Fixes Integrated:** 
    - Fix: Agent 2 review override (force evaluation).
    - Fix: Statuses defaulting to 'human' incorrectly.
    - Fix: Rejected jobs missing from database.
    - Fix: Expiry date extraction.


## Testing Decisions
- **Parser Testing:** We will prioritize unit tests for the `SeekParser` using a library of saved HTML snapshots. Tests will verify that changes in Seek's UI are caught without needing a browser.
- **Repository Testing:** We will test the `JobRepository` against an in-memory SQLite database to verify state transitions and persistence logic.
- **Strategy Testing:** Each AI Strategy (Triage, Evaluation) will have its prompt/schema tested against mock LLM responses.
- **Integration Testing:** We will use a "Mock Pipeline" to verify the end-to-end flow from a fake scrape to a fake evaluation result.

## Out of Scope
- Expanding to other websites (TradeMe, etc.) is out of scope for this refactor but the architecture must support it.
- Moving the TUI to a web-based dashboard.
- Advanced "Human-in-the-loop" UI for editing prompts.

## Further Notes
- This refactor prioritizes **Depth** over **Shallow extraction**. 
- We will strictly follow the "Pydantic at the gate, Dataclasses in the engine" (or pure Pydantic) pattern as discussed.
- The `TriageSorter` and `JobEvaluator` classes will be deleted in favor of the new Pipeline Runner.
