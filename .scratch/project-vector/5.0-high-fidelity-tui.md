# PRD: High-Fidelity TUI & Job Lifecycle Management

## Problem Statement

The current Project Vector TUI feels like a basic review tool rather than a comprehensive application. Users lack visual clarity on job statuses and decision sources (Agent 1 vs Agent 2 vs Human). There is also no way to manage the full lifecycle of a job—such as manual deletion, validity checking for expired listings, or triggering deep evaluations—without returning to the command line.

## Solution

Transform the TUI into a "high-fidelity" application that provides rich visual feedback, row-level row actions, and automated maintenance tasks. The TUI will track who made the last decision, visually differentiate between various states using emojis and colors, and handle background tasks like validity checking and batch evaluations.

## User Stories

1. As a user, I want to see a clear visual indication of a job's status (new, high-pass, edge-case, shortlisted, discarded, rejected, expired) and who made the last decision (robot 🤖 vs human 👤), so I can quickly identify which jobs need my attention.
2. As a user, I want to see which jobs have expired, so I don't waste time looking at dead listings.
3. As a user, I want to trigger a deep evaluation (Agent 2) on a specific job regardless of its current status, so I can override Agent 1's initial triage.
4. As a user, I want to manually delete jobs from the TUI, so I can keep my database clean.
5. As a user, I want to run the full evaluation pipeline from within the TUI when no digests exist, so I don't have to switch to the CLI.
6. As a user, I want to undo a staged change (promote/reject/delete) before saving, so I can correct mistakes.
7. As a user, I want the TUI to automatically check for job validity in the background, so the information is always up-to-date without blocking my workflow.
8. As a user, I want rejected jobs to be automatically marked for deletion once they expire, so they don't reappear in future scrapes.
9. As a user, I want to see a progress indicator when a background check is running, so I know the system is active.
10. As a user, I want the job list to regain focus automatically when I navigate back from other views (like Suggestions or Digests).

## Implementation Decisions

### Schema Changes
- Add `last_checked_at` (timestamp) to track validity checks.
- Add `is_valid` (boolean/integer) to store the result of the validity check.
- Add `last_decision_by` (text: 'robot' or 'human') to track the source of the latest status change.
- Add `expiration_date` (timestamp) to support smart maintenance logic.

### Core Logic Updates
- **Collector:** Assign a default expiration date (Scrape Date + 30 days) to new jobs.
- **Sorter (Agent 1):** Set `last_decision_by = 'robot'` when triaging.
- **Evaluator (Agent 2):** Introduce explicit `shortlisted` and `discarded` verdicts and set `last_decision_by = 'robot'`.

### TUI (ReviewApp) Enhancements
- **Visual Mapping:** Use high-fidelity emojis (✅, ❌, ❓, ✨, ⏰, 🗑️) combined with decision-source icons (🤖, 👤).
- **Styling:** Use background colors (Bright Green, Dim Red, Yellow, Gray) to denote urgency and grouping.
- **Background Tasks:** Use Textual `@work` workers for non-blocking HTTP validity checks and LLM evaluations.
- **Validity Logic ("Clean Sweep"):** 
    - Check active jobs on trigger.
    - Check rejected jobs only if past their `expiration_date`.
    - Auto-mark expired rejected jobs for deletion.
- **Row-Level Actions:** Add keybindings for "Force Digest" (`D`), "Verify Row" (`v`), and "Mark for Deletion" (`x`).
- **Undo Logic:** Add `Backspace` to clear staged changes for the selected row.

## Testing Decisions

- **Validity Checker:** Test the URL checking logic with mocked HTTP status codes and redirection targets.
- **State Machine:** Verify that `last_decision_by` correctly flips between 'robot' and 'human' based on user interaction vs automated triage.
- **Clean Sweep:** Verify that rejected jobs are ignored by the validity checker until they expire, and then correctly marked for deletion.

## Out of Scope

- Real-time background scraping (scraping remains a CLI task).
- Bulk editing of job details (only status and notes are editable).
- Multi-user support or collaborative review features.

## Further Notes

The "Clean Sweep" logic is critical to prevent "ghost" jobs—listings that were rejected and deleted but reappear in future scrapes because they are still live on the source site. The database must remain the "memory" of these rejections until the listing itself is gone.
